# Knowledge authoring

Knowledge here is read by every model, including weaker ones, and it rots unless something checks it. This
skill decides where a lesson lives, how it is written, how a skill is tested, and how it all stays true. It
prevents the two usual failures: a doc that reads well but contradicts the code, and a skill that never
fires or was never run. Mechanical rules are enforced by `~/.claude/scripts/knowledge-lint.py`, which gates the
auto-push; this skill covers the judgment the linter cannot make.

## 1. Decide where it lives

| It is... | It goes in... |
|---|---|
| A rule a script can check (format, length, a broken link, a forbidden pattern) | `knowledge-lint.py`, an app lint rule, a type, or a test. Never prose first. |
| A behavior that must hold in every session | `~/.claude/RULES.md` (always loaded, so keep it short) |
| A live fact (port, container, hostname, image, volume) | Nowhere by hand: `~/.claude/FLEET.md` is generated by `~/.claude/scripts/fleet-facts.py` |
| A stable machine fact (path, account, host) | `~/.claude/ENVIRONMENT.md`, or a project `AGENTS.md`, never both |
| Task-shaped knowledge loaded on demand | a skill, or a gotcha in an existing skill |
| How to drive one app and prove its behavior | that repo's `.claude/skills/verify-<app>/` (see `verify-ui-live`) |
| Project context, commands, domain rules | that project's `AGENTS.md` |
| A dated event, user preference, or cross-project state | a memory file plus its `MEMORY.md` line |
| Dispatch only ("when X, load Y") | a row in the RULES.md router table, never a dispatch-only skill |
| The incident or measurement behind a rule | the skill's `references/history.md`, or `~/.claude/HISTORY.md` for RULES and ENVIRONMENT |

One fact lives in one place. If you are copying a paragraph between two files, one of them should be a pointer.

Done when: you can name the one file the lesson goes in, and no other file already says it.

## 2. Write it to the house style

Follow `references/skill-style.md` for every SKILL.md: a description of what and when (never a summary of the
steps), a body of at most 150 lines and under 15,000 characters, steps that end in `Done when:`, red flags only
when earned here, full sentences, no long dashes, no live facts, and history moved to `references/history.md`.

- A new skill needs a router row in RULES.md in the same change, or it will not fire for weaker models.
- Name the failure the skill prevents in its opening paragraph; rules whose cost is visible get followed.
- Encode only what was earned on this box (a gotcha, a decision, a measured fact). Generic advice a model already knows is noise.
- Run the no-op test on every sentence: if the model would do the same thing without it, delete the whole sentence, not a few words. Settle a disagreement about a sentence by running the skill, not by arguing.
- Point at a file, command, or `--help` output instead of copying what it says. A copy is a cache that goes stale; copy only what an agent cannot find by looking (the reason, the unwritten convention, the gotcha).
- Use leading words: name a recurring idea with one short word the model already knows (a check that goes *red* on the bug, a *tight* loop) and repeat that word, instead of spelling out the same idea in a sentence each time. A familiar word brings its meaning for free; an invented one must be defined.
- Group project invariants by subject, never by version: a `## v3 rules` section grows until it contradicts itself.
- Tracker files (FEATURES.md, PLAN.md) describe the code as it is. Write a status line from the code you just read, and mark a spec item superseded (with the reason) when a later decision made it unreachable.

Done when: the artifact passes the checks in step 6, and every sentence passed the no-op test.

## 3. Build and test a skill

For a new skill or a real rewrite, run the measured loop in `references/skill-building.md`: capture intent, draft,
run two or three realistic prompts with and without the skill, grade, show the user the viewer, revise, then
tune the description. Run its scripts from this directory as `python -m scripts.<name>` (for example
`cd ~/.agents/skills/knowledge-authoring && python3 -m scripts.quick_validate <skill-dir>`), because they import
each other as a package. For a small edit, skip the eval loop but walk the edited skill through two real requests
from past chats, one of them a case where it misfired: read the skill as the agent would and say what it now does
differently. Skip even that only when the user says so, and say what you skipped.

Done when: `python3 -m scripts.quick_validate <skill-dir>` prints `Skill is valid!`, and either the user approved the
eval outputs or you said why the loop was skipped.

## 4. The HARVEST inbox

`~/.claude/HARVEST.md` collects lessons under `## Pending`; they leave it under `## Processed`. Deciding what each
one becomes (the five-question filter) lives in `retro` since 2026-10-16. This skill then writes the accepted ones
to the house style and runs the ripple check.

Done when: every lesson `retro` accepted is written, and lint is clean.

## 5. Ripple check (every knowledge change)

- Renamed or deleted something: `grep -rn "<old-name>" ~/.claude/*.md ~/.agents/skills --include="*.md"` (through `rtk proxy` when you need the full list) plus affected project docs, and fix every hit in the same change.
- Created something: add its router row; wire it into the skills that should read or write it; whitelist new files under `~/.claude` in `.gitignore`; add a lint check if it can rot; update dev-system `REBUILD.md` or `INSTALL.md` if a rebuild needs it; resolve trigger overlap with existing skills through a precedence note in the router.
- Changed a contract: grep for skills that name it and confirm each described interaction still holds.

Done when: the reply says "Ripple: N references checked, M files updated", and a rerun of the grep finds no old name.

## 6. Before you finish

```bash
python3 ~/.claude/scripts/knowledge-lint.py                 # zero ERROR lines
python3 ~/.claude/scripts/knowledge-preserve.py <skill>     # after rewriting a skill: 0 lost tokens
~/.agents/skills/agent-tool-bench/references/router-eval/run-skill.sh <skill>   # after a description change
# after a RULES.md router change: the full sweep in router-eval/README.md ("When to run what" 3)
```

- Agents writing knowledge own a whole skill directory, never single files across directories. The Stop hook lints, holds the push on errors, and otherwise commits whatever exists, so before ending a turn while agents still write, create `~/.claude/knowledge-hold` (one line: why) and delete it once their work passes lint and the preserve check.
- If `knowledge-lint.py` itself is wrong about a case, fix the linter in its own change rather than working around it.

Done when: both commands above print zero errors and zero lost tokens, pasted in the reply.

## Red flags

- Pasting a solved gotcha's fix into a description "so it triggers". One description reached 3,137 characters of answers the router never needed.
- Shipping a new artifact without its router row and consumers. HARVEST.md shipped unregistered in two consumers until the user caught it.
- Two agents restructuring one skill directory, or a restructure left running across a turn boundary. A reference file went to 0 bytes and was committed as if finished.
- A tracker line copied from the plan instead of the code. A status doc claimed a feature for two days that was never built.
- A command written into an `AGENTS.md` that was never run. A documented test command stayed broken for weeks.

## Gotchas

- A rule that agents keep breaking is a missing check, not a missing sentence. The em-dash ban was re-policed by hand for months before the linter enforced it.
- A half-finished restructure looks finished: a reference file left at 0 bytes or orphaned still loads without error. The linter catches dangling and orphaned references and empty files.
- A crashed git can leave `.git/index.lock` and silently stop all commits; the auto-push now clears a stale one. Check `~/.claude/skills-autopush.log` when commits stop appearing.
- The eval viewer cannot open a browser on this headless box. Pass `--static <output_path>` to `eval-viewer/generate_review.py`, then copy the downloaded `feedback.json` into the workspace.
- A trigger eval made of one-step queries ("read this PDF") measures nothing, because the agent answers those without any skill. Use substantive queries and near-miss negatives.
- A check that must bind every agent lives in one script with a thin adapter per agent (exit 2 plus stderr denies; a broken payload fails open, a tool error inside a git hook fails closed). The pattern: `~/.claude/scripts/agent-guard.py` and `~/.claude/git-hooks/`.
